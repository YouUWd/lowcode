# Lumina 企业级低代码平台 - 产品需求文档 (PRD)

## 1. 业务背景与产品定位
Lumina 是一款专为企业级复杂业务设计的**模块化低代码数据建模与流程管理平台**。在企业数字化转型中，核心痛点包含：
- **元数据建模多变**：不同业务模块对数据源、表结构、字段属性以及表间关联（1:1、N:1、1:N、N:M）的要求频繁变动。
- **列级安全性要求高**：系统必须支持根据不同的用户角色（如 admin, editor, viewer）进行颗粒度达到字段（列）级的读写权控制，支持黑白名单以及敏感字段脱敏。
- **业务流程高度耦合**：传统审批流深度绑定业务表，导致业务系统臃肿。需要一款统一的、零侵入的轻量级工作流引擎，将业务数据草稿（Payload）与流程运行时状态分离，仅在审批终审通过时以事件驱动方式落库真实业务表。

Lumina 基于 **Node.js / NestJS / TypeScript / Knex.js** 技术栈构建，通过**配置型元数据引擎**实现数据源与实体的动态拼装，结合**列级安全控制 (CLS)** 与 **v2 审批流引擎**，向企业提供灵活、安全、可组装的数据中台支撑。

## 2. 核心功能需求

### 2.1 动态元数据建模与查询引擎 (Meta Engine & Query Engine)
系统通过在配置库中定义元数据，实现物理数据库结构的抽象和动态查询：
1. **多数据源抽象 (`datasource_meta`)**：支持管理多个数据源（如 SQLite, MySQL），实现跨库、跨服务的动态数据建模。
2. **逻辑实体与表字段管理 (`table_meta`, `field_meta`, `module_table_meta`)**：
   - 动态配置表（如 orders, customer_profiles）及逻辑展示名称。
   - 动态配置字段（ID、类型、展示 Label，如 string, number, decimal, datetime）。
   - 实现模块与物理表的多对多绑定。
3. **复杂实体关联解析 (`relation`, `relation_field_meta`)**：
   - 支持 **1:1 / N:1** 关联（如订单与其关联的客户扩展表）：主查询时通过 `LEFT JOIN` 一次性关联加载。
   - 支持 **1:N** 关联（如订单与订单明细从表）：异步执行独立子查询，用主键集合批量拉取，减少数据库往返与笛卡尔积。
   - 支持 **N:M 多对多** 关联（如订单与标签表通过中间表关联）：支持解析中间件，通过两次 1:N 映射自动聚合多对多标签数据。
4. **混合计算引擎 (Hybrid Computation)**：
   - **数据库级计算（下推）**：将日期格式化、年龄/工龄计算以 raw SQL 的形式在数据库端完成，并能自适应 SQLite 和 MySQL 方言。
   - **BFF 级计算（上拉）**：对于敏感数据掩码（`MASK_SENSITIVE`）、字典转换（`DICT_MAP`）、物理字段合并等，在服务内存中读取物理字段并转换为逻辑 DTO。

### 2.2 Unix 风格列级安全控制 (Column-Level Security, CLS)
实现细粒度白名单权限控制：
1. **系统角色与白名单机制**：定义系统角色（如 `admin` 管理员, `editor` 编辑员, `viewer` 查看员）。只有在权限配置表中有显式关联的字段才允许访问（默认拒绝）。
2. **Unix 风格权限值 (Bitmask Permission)**：
   - 字段权限值（`perm_value`）使用类 Unix 的数值掩码形式（如 `4` 为只读 READ，`7` 为完全读写控制）。
   - 支持对不同角色配置对特定字段的权限值（例如 `viewer` 只对基础字段有 `4` 只读权，对 `remark` 无权限则不可见；`editor` 具有部分字段的写和更改权限 `7`）。
3. **动态安全拦截**：
   - 字段级过滤：在主子查询拼装字段时，剔除用户所属角色没有 `READ` (包含相应权限位) 的字段。
   - 敏感字段脱敏：对于无 `READ` 权限但需要展示的敏感列，动态将其重写为脱敏转换规则（如全星号掩盖 `MASK_SENSITIVE`）。

### 2.3 零侵入工作流引擎 v2.0 (Workflow Engine)
实现流转过程与业务实体物理表的 **100% 盲视解耦 (Zero-Intrusion Decoupling)**：
1. **独立流程上下文**：业务数据草稿、操作类型（`INSERT`, `UPDATE`, `DELETE`, `CUSTOM`）在审批中统一作为 `payload` (JSON) 暂存在工作流实例表，物理业务表无任何 status 列。
2. **指针双向链表路由**：配置使用 `up_id` 与 `next_id` 实现双向链表式的节点路由，支持条件跳转（`condition`）与超时/自动跳转。
3. **Fork-Join 并行组任务 (`parallel_group`)**：
   - 一个审批节点可配置多个并行的分支任务（如财务审批分支与教务核准分支并发）。
   - 采用 Join 汇聚机制，分支间状态互不干扰，当且仅当组内所有分支任务均为 `PASS` 时，工作流指针向下一步（`next_id`）推进。
4. **数据变更与智能靶向回退 (`smart_rollback`)**：
   - 审批途中如发生申请数据修改，引擎可根据配置的回退策略将当前所有 `PENDING` 任务置为 `INVALIDATED`。
   - 靶向重置（回退）特定分支节点（例如仅将财务分支的历史状态置为 `INVALIDATED` 并重新生成该分支任务），避免无关分支（如已通过的 IT 分支）重复审批。
5. **事件驱动落地（Event-Driven Finalization）**：
   - 当流程推进到 `next_id = 0` 时，流程结束，触发 `workflow.process.approved.{module_id}` 全局事件，由业务层模块订阅并最终写入物理业务表。

## 3. 非功能性需求
1. **高性能数据拼装**：避免在 1:N / N:M 关联中循环查询数据库（不产生 `N+1` 查询问题），子表关联统一使用外键 `whereIn` 批量查询后在 BFF 层组装。
2. **极简迁移与高内聚**：各服务模块强内聚，工作流只读写其专有的 4 张工作流配置与运行时表，各模块解耦完全通过 NestJS 内置事件实现。
